# Source and provenance: pcap-threat-stats

Compiled on 2026-10-08 from two curated Agent Skills, copied verbatim here:

| Source | Content |
|---|---|
| `pcap-analysis/SKILL.md` | Guide to computing PCAP network statistics with scapy: counts, entropy, graph, temporal, PCR, flows, ppm time series, CSV writing, detection questions, and common issues |
| `pcap-analysis/pcap_utils.py` | Tested helper module that implements all of the above. Also copied unchanged to `scripts/pcap_utils.py` so the client task can import it |
| `threat-detection/SKILL.md` | Exact thresholds for port scan, DoS, beaconing, and benign traffic, with worked examples |

Both skills describe one workflow: compute the metric set from a capture, apply the
thresholds, and fill a `metric,value` stats CSV. The task environment's Dockerfile
(ubuntu 24.04, python3, scapy 2.5.0, pandas, numpy) and `network_stats_template.csv`
shaped the I/O. The template is bundled as `assets/network_stats_template.csv` and used
only when the target CSV does not exist. The environment's ground-truth extraction
scripts were deliberately NOT read or used. The pack follows the curated skills' definitions only.

## Intent

Make one fast, deterministic pass do everything both skills prescribe, so the agent
cannot drift from the calibrated thresholds or the "unique IPs, not packets" degree rule.
Leave the agent only the work that depends on the task wording.

## Graph and step-kind choices

1. **`analyze-capture` (execution, `scripts/analyze_pcap.py`)**. Every metric is a
   deterministic computation, and every detection rule is a fixed numeric threshold.
   Both belong in a script per AIP best practice. The script streams with `PcapReader`
   in one pass instead of `rdpcap` (the source's large-PCAP advice) and reproduces the
   layer checks, rounding, and thresholds of `pcap_utils.py` exactly. The 2026-10-08
   build cross-checked it against `pcap_utils.py` on the real 114k-packet capture and
   on synthetic captures, with 0 mismatches across 32 metrics and verdicts. It fills the
   CSV in place, keeping the header and `#` rows, and lists template rows it cannot
   map. If scapy is not importable, it tries a single pip bootstrap.
2. **`scope-check` (decision, noul `extra_work_needed`)**. Whether the task asks for more
   than the CSV is a judgment over free-text instructions with a yes/no answer space.
   The threshold is low (0.3) because a missed requirement costs more than an extra
   pass through the client task.
3. **`by-scope` (router)** branches on the noul.
4. **`complete-outputs` (client_task)**. Unknown metric rows, prose answers, or extra
   files must be generated by the agent. The template pins the agent to the script's
   values and to the exact thresholds. `references/metric-definitions.md` carries every
   definition for on-demand loading.
5. **`end`** holds `metrics` (all values and verdicts) and `csv_written`.

## Small, documented choices beyond the sources

- `avg_packet_size` is rounded to 4 dp. The sources specify no rounding for it.
  `duration_seconds` is rounded to 6 dp. All other rounding follows `pcap_utils.py`:
  entropy 4 dp, density 6 dp, ppm_avg 2 dp, iat_mean and iat_variance 6 dp, iat_cv 4 dp.
- Detectors compare the rounded `packets_per_minute_avg` and `iat_cv`, as in the source's
  usage pattern, where the helpers' rounded outputs feed the detectors.
- With fewer than 2 timestamps, the source helpers return None and then crash. The script
  instead sets the IAT metrics to 0 and `has_beaconing` to false, because there is no
  interval to judge.
- Template rows the script does not know are left empty rather than dropped. The source's
  CSV snippet silently dropped them.
- `total_packets` and `dominant_protocol` from the source are computed. They are written to
  the CSV only if the template has those rows.

## Functional-test notes (2026-10-08)

- `aip run` was tested through both router branches. The `false` branch used a synthetic benign capture with a template-only task. The `true` branch used a synthetic capture with a SYN scan, an unknown template row, and a written-note request. Two fresh agent sessions also completed the procedure.
- Feedback applied: the scope-check now says that "decide whether benign/scan/DoS/beaconing" is covered by the CSV's true/false rows. The client task no longer asks for `metrics`/`csv_written` to be posted back. The script step no longer implies it must run only in the container.
- Known limitation kept on purpose: the curated source defines beaconing as a single capture-wide IAT CV < 0.5, not per host. A per-host beacon under heavy background traffic would therefore not trip it. The source warns that any other rule gives wrong results for this task type, so the rule is kept as is.
